* Scope
:PROPERTIES:
:CUSTOM_ID: scope
:END:

What ~i2c_master~ has to do, seen from outside, and how each statement is
shown to hold.  It does not say how the block is built (design description)
or what happens at its ports clock by clock (ICD); it is what those two
documents and the testbench are checked against.

Only what the block does is a requirement here.  What it does not do, and
what it does with commands it should not get, is in the
[[file:i2c_master_icd.org::#limitations][limitations]] and the [[file:i2c_master_icd.org::#illegal-sequences][illegal sequences]] of the ICD.

- Parent :: none.  The block is a worked example of the templates; a real
  block names the system requirement or ticket it exists for
- Interface :: [[file:i2c_master_icd.org::#scope][i2c_master ICD]]
- Design :: [[file:i2c_master_hdd.org::#overview][i2c_master design description]]
- Verification :: [[file:i2c_master_vplan.org::#test-cases][i2c_master verification plan]]
- Traceability :: [[file:i2c_master_rtm.org::#matrix][i2c_master traceability matrix]]

* Reading a requirement
:PROPERTIES:
:CUSTOM_ID: reading
:END:

- One ID per statement, ~REQ-nnn~, never reused.  Gaps are fine.
- One "shall" per requirement, and a rationale that answers "does the
  application need this?".
- METHOD is T (a test case of ~tb_i2c_master~), A (analysis: a report or a
  calculation), I (inspection: reading the code) or D (demonstration).
- RESULT is PASS only for what was run and passed; OPEN means not yet run.
  Nothing of method A or I was run for this example: no synthesis, no CDC
  report, no review.
- C_Q is the quarter period in clocks, defined in the
  [[file:i2c_master_icd.org::#bus-timing][bus timing of the ICD]].

** Functional

*** REQ-001 START condition
:PROPERTIES:
:CUSTOM_ID: REQ-001
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-02][TC-02]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][S_START]]
:ICD:      [[file:i2c_master_icd.org::#start-hold][start-hold]]
:MONITOR:  p_tw_start_hold
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall make a START condition before the byte of a command taken
  with ~cmd_start~ while no transaction is open.
- Rationale :: Every I2C transfer begins with a START.  It is a command bit so that
  software decides where a transfer begins, not the block.

*** REQ-002 Repeated START
:PROPERTIES:
:CUSTOM_ID: REQ-002
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-05][TC-05]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][S_START]]
:ICD:      [[file:i2c_master_icd.org::#start-setup][start-setup]]
:MONITOR:  p_tw_start_setup
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall make a repeated START when a command with ~cmd_start~ is
  taken while a transaction is open.
- Rationale :: Reading a register of most devices needs a change of direction without
  letting go of the bus.  Without it software would have to send a STOP, and
  such devices then forget the register number.

*** REQ-003 Write a byte and report the acknowledge
:PROPERTIES:
:CUSTOM_ID: REQ-003
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-02][TC-02]], [[file:i2c_master_vplan.org::#TC-03][TC-03]]
:DESIGN:   [[file:i2c_master_hdd.org::#datapath][datapath]]
:ICD:      [[file:i2c_master_icd.org::#response][response]]
:MONITOR:
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall send ~cmd_data~ most significant bit first and report in
  ~rsp_nack~ whether the ninth bit was left unacknowledged.
- Rationale :: The acknowledge of the address is the only way software learns that a
  device is absent or busy.

*** REQ-004 Read a byte and answer it
:PROPERTIES:
:CUSTOM_ID: REQ-004
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-04][TC-04]]
:DESIGN:   [[file:i2c_master_hdd.org::#datapath][datapath]]
:ICD:      [[file:i2c_master_icd.org::#response][response]]
:MONITOR:
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall read eight bits into ~rsp_data~, most significant bit
  first, and answer with NACK when ~cmd_nack~ is set and with ACK otherwise.
- Rationale :: A slave keeps sending until it sees a NACK.  The last byte of a read must
  be answered with one or the slave holds SDA at the next STOP.

*** REQ-005 STOP condition
:PROPERTIES:
:CUSTOM_ID: REQ-005
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-06][TC-06]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][S_STOP]]
:ICD:      [[file:i2c_master_icd.org::#stop-setup][stop-setup]]
:MONITOR:  p_tw_stop_setup
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall make a STOP condition after the byte of a command with
  ~cmd_stop~, or at once when the command has no byte and a transaction is
  open.
- Rationale :: The STOP alone is needed after a NACKed address, when there is no byte
  left to attach it to.

*** REQ-006 Clock stretching
:PROPERTIES:
:CUSTOM_ID: REQ-006
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-07][TC-07]], [[file:i2c_master_vplan.org::#TC-20][TC-20]]
:DESIGN:   [[file:i2c_master_hdd.org::#timer][quarter timer]]
:ICD:      [[file:i2c_master_icd.org::#stretch-wait][stretch-wait]]
:MONITOR:  p_tw_stretch_wait
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall not go on with a transfer while a slave holds SCL low.
- Rationale :: Slaves stretch the clock when they need time for a byte.  A master that
  ignores it samples bits the slave has not sent yet.

*** REQ-007 SDA moves only while SCL is low
:PROPERTIES:
:CUSTOM_ID: REQ-007
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-02][TC-02]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][step sequence]]
:ICD:      [[file:i2c_master_icd.org::#sda-change][sda-change]]
:MONITOR:  p_tw_sda_change
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall change SDA while SCL is high only to make a START or a
  STOP that a command asked for.
- Rationale :: Any other change of SDA while SCL is high is a START or STOP to every
  slave on the bus and ends or restarts their transfers.

*** REQ-008 Every command is answered
:PROPERTIES:
:CUSTOM_ID: REQ-008
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-12][TC-12]], [[file:i2c_master_vplan.org::#TC-13][TC-13]], [[file:i2c_master_vplan.org::#TC-14][TC-14]], [[file:i2c_master_vplan.org::#TC-15][TC-15]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][S_IDLE]]
:ICD:      [[file:i2c_master_icd.org::#illegal-sequences][illegal sequences]]
:MONITOR:  p_tw_rsp_per_cmd
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall answer every command it takes while ~rst~ is low with one
  response, whatever the combination of its fields.
- Rationale :: A driver that waits for a response must not hang on its own mistake.
  The hardware stays usable without the software being correct.

** Interface

*** REQ-020 Command handshake
:PROPERTIES:
:CUSTOM_ID: REQ-020
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-08][TC-08]]
:DESIGN:   [[file:i2c_master_hdd.org::#command-interface][command interface]]
:ICD:      [[file:i2c_master_icd.org::#ready-busy][ready-busy]]
:MONITOR:  p_tw_ready_busy
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall take a command only in a clock in which ~cmd_valid~ and
  ~cmd_ready~ are both 1.
- Rationale :: The same valid/ready rule as the streams in the rest of a design, so a
  FIFO or a state machine can feed the block without glue.

*** REQ-021 Response pulse
:PROPERTIES:
:CUSTOM_ID: REQ-021
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-08][TC-08]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][S_DONE]]
:ICD:      [[file:i2c_master_icd.org::#rsp-pulse][rsp-pulse]]
:MONITOR:  p_tw_rsp_pulse
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall raise ~rsp_valid~ for exactly one clock for each response.
- Rationale :: A pulse can be counted and can write a FIFO.  A level would need an
  acknowledge port that nothing else in the interface needs.

*** REQ-022 Response data holds
:PROPERTIES:
:CUSTOM_ID: REQ-022
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-12][TC-12]]
:DESIGN:   [[file:i2c_master_hdd.org::#structure][rsp_data, rsp_nack]]
:ICD:      [[file:i2c_master_icd.org::#rsp-stable][rsp-stable]]
:MONITOR:  p_tw_rsp_stable
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall keep ~rsp_data~ and ~rsp_nack~ unchanged from one response
  to the next.
- Rationale :: Software behind a register interface reads the result some time after
  the pulse.

*** REQ-023 Open-drain bus pins
:PROPERTIES:
:CUSTOM_ID: REQ-023
:METHOD:   I
:TEST:     reading the entity
:DESIGN:   [[file:i2c_master_hdd.org::#overview][overview]]
:ICD:      [[file:i2c_master_icd.org::#ports][ports]]
:MONITOR:
:RESULT:   OPEN
:STATUS:   proposed
:END:
- Shall :: The block shall pull the bus lines low or release them, and never drive
  them high.
- Rationale :: I2C is a wired-AND bus.  A driven 1 against a slave that pulls low is a
  short circuit.

** Performance

*** REQ-040 SCL low and high time
:PROPERTIES:
:CUSTOM_ID: REQ-040
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-09][TC-09]]
:DESIGN:   [[file:i2c_master_hdd.org::#timer][quarter timer]]
:ICD:      [[file:i2c_master_icd.org::#scl-low][scl-low]], [[file:i2c_master_icd.org::#scl-high][scl-high]]
:MONITOR:  p_tw_scl_low, p_tw_scl_high
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The SCL low phase and the SCL high phase shall each last at least
  2 * C_Q clocks, with C_Q = ~G_CLK_HZ~ / (4 * ~G_SCL_HZ~) rounded down.
- Rationale :: The slowest device on the bus sets the minimum phase lengths, and the
  integrator picks ~G_SCL_HZ~ from them.  The calculation is in the
  [[file:i2c_master_icd.org::#bus-timing][bus timing table of the ICD]].

*** REQ-041 Command latency
:PROPERTIES:
:CUSTOM_ID: REQ-041
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-06][TC-06]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][control FSM]]
:ICD:      [[file:i2c_master_icd.org::#cmd-latency][cmd-latency]]
:MONITOR:  p_tw_cmd_latency
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: A response shall arrive the number of clocks given in the ICD after its
  command was taken, plus the clocks in which SCL was held low.
- Rationale :: Software timeouts and the byte rate follow from it: a byte takes
  37 * C_Q + 20 clocks, 92.7 us with the default generics.  This example
  has no system budget above it; the number is written down so that a
  later request to make it faster has something to be held against.

*** REQ-043 START and STOP timing
:PROPERTIES:
:CUSTOM_ID: REQ-043
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-09][TC-09]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][step sequence]]
:ICD:      [[file:i2c_master_icd.org::#start-setup][start-setup]], [[file:i2c_master_icd.org::#start-hold][start-hold]], [[file:i2c_master_icd.org::#stop-setup][stop-setup]], [[file:i2c_master_icd.org::#bus-free][bus-free]]
:MONITOR:  p_tw_start_setup, p_tw_start_hold, p_tw_stop_setup, p_tw_bus_free
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: START hold, repeated START setup, STOP setup and the bus free
  time after a STOP shall each last at least 2 * C_Q clocks.
- Rationale :: Standard-mode devices need 4.0 to 4.7 us for these four
  times (NXP UM10204, Rev. 7.0, 1 October 2021, Table 11).  One quarter
  period is 2.5 us at 100 kHz and too short; two quarters are 5.0 us.  The
  [[file:i2c_master_icd.org::#spec-timing][comparison in the ICD]] has the numbers.

*** REQ-042 Clock frequency
:PROPERTIES:
:CUSTOM_ID: REQ-042
:METHOD:   A
:TEST:     timing report
:DESIGN:   [[file:i2c_master_hdd.org::#clocks][clocks]]
:ICD:      [[file:i2c_master_icd.org::#clocks][clocks]]
:MONITOR:
:RESULT:   OPEN
:STATUS:   proposed
:END:
- Shall :: The block shall meet timing at ~G_CLK_HZ~ on the target device with the
  project constraints.
- Rationale :: One system clock for the block and its user logic.  No synthesis was run
  for this example, so the result is open.

** Reset and start-up

*** REQ-060 Reset state
:PROPERTIES:
:CUSTOM_ID: REQ-060
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-01][TC-01]], [[file:i2c_master_vplan.org::#TC-16][TC-16]]
:DESIGN:   [[file:i2c_master_hdd.org::#clocks][reset]]
:ICD:      [[file:i2c_master_icd.org::#rst-release][rst-release]]
:MONITOR:  p_tw_rst_release
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: One clock after ~rst~ was sampled high the block shall be idle and ready,
  with both bus lines released, from any state.
- Rationale :: A block that keeps SCL or SDA low after reset blocks the bus for every
  other device, and software may send a command as soon as it runs.

*** REQ-061 Bus clear
:PROPERTIES:
:CUSTOM_ID: REQ-061
:METHOD:   T
:TEST:     [[file:i2c_master_vplan.org::#TC-15][TC-15]], [[file:i2c_master_vplan.org::#TC-18][TC-18]]
:DESIGN:   [[file:i2c_master_hdd.org::#fsm][S_BYTE]]
:ICD:      [[file:i2c_master_icd.org::#bus-clear][bus-clear]]
:MONITOR:  p_tw_byte_no_start
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall offer a command that makes nine SCL pulses and a STOP
  without a START.
- Rationale :: A reset or a CPU restart in the middle of a read can leave a slave
  holding SDA low.  Nothing but clock pulses makes it let go, and the block
  has no other means to make them.  See the [[file:i2c_master_icd.org::#recovery][recovery sequence]].

** Design constraints

*** REQ-080 Language and style
:PROPERTIES:
:CUSTOM_ID: REQ-080
:METHOD:   I
:TEST:     design review
:DESIGN:   [[file:i2c_master_hdd.org::#structure][structure]]
:ICD:
:MONITOR:
:RESULT:   OPEN
:STATUS:   proposed
:END:
- Shall :: The block shall be written in VHDL-2008 in the two-process style with a
  synchronous, active-high reset.
- Rationale :: One coding style and one reset strategy for all blocks of a design.

*** REQ-081 Synchronized bus inputs
:PROPERTIES:
:CUSTOM_ID: REQ-081
:METHOD:   I, A
:TEST:     CDC report
:DESIGN:   [[file:i2c_master_hdd.org::#cdc][crossings]]
:ICD:      [[file:i2c_master_icd.org::#cdc][crossings]]
:MONITOR:
:RESULT:   OPEN
:STATUS:   proposed
:END:
- Shall :: The block shall pass ~scl_i~ and ~sda_i~ through a synchronizer of two
  flip-flops before any other logic uses them.
- Rationale :: The bus is asynchronous to ~clk~, and a slave moves SDA and SCL at any
  time.

*** REQ-082 Self-checking testbench
:PROPERTIES:
:CUSTOM_ID: REQ-082
:METHOD:   D
:TEST:     run of ~tb_i2c_master~ and of ~tb/mutants.txt~
:DESIGN:
:ICD:      [[file:i2c_master_icd.org::#scope][ICD]]
:MONITOR:
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall ship with a testbench that prints ~TEST PASSED~ only when
  every test case passed, with a monitor for each ICD clause that has been
  seen to fire.
- Rationale :: A verdict can be checked by a script.  A monitor that has never fired
  may be dead, and then a silent run proves nothing.
