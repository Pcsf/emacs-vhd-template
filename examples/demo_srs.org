* Reading a requirement
:PROPERTIES:
:CUSTOM_ID: reading
:END:

- One ID per statement, ~REQ-NNN~, never reused once published.
  Gaps are fine; renumbering is not.
- One "shall" per requirement.  "And" usually means two requirements.
- Every requirement has a rationale: the question to answer is "does the
  application really need this?".  No rationale, no requirement.
- Every requirement names a verification method and, once it exists, the
  test case or analysis that verifies it.  These are properties of the
  headline, with the design element and the ICD clause, and the
  traceability matrix is generated from them:

| Method | Meaning                                                 |
|--------+---------------------------------------------------------|
| T      | Test: a numbered test case in ~tb_demo~ or on hardware  |
| A      | Analysis: calculation or report (timing, CDC, resource) |
| I      | Inspection: reading the code or the constraint file     |
| D      | Demonstration: it visibly works, no measurement         |

- STATUS is one of proposed, approved, verified, deleted; RESULT is PASS,
  FAIL, OPEN (not yet run), or N/A with a reason.

** Functional

*** REQ-001 Start begins exactly one operation
:PROPERTIES:
:CUSTOM_ID: REQ-001
:METHOD:   T
:TEST:     [[file:demo_vplan.org::#TC-02][TC-02]]
:DESIGN:   [[file:demo_hdd.org::#fsm][FSM]]
:ICD:      [[file:demo_icd.org::#reg-control][CONTROL]]
:MONITOR:
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall begin one operation on each 0 to 1 transition of
  ~start~ sampled while it is idle.
- Rationale :: Level-triggered start lets the host hold the line without a
  timing requirement on the pulse width.

*** REQ-002 Busy covers the whole operation
:PROPERTIES:
:CUSTOM_ID: REQ-002
:METHOD:   T
:TEST:     [[file:demo_vplan.org::#TC-03][TC-03]]
:DESIGN:   [[file:demo_hdd.org::#fsm][FSM]]
:ICD:      [[file:demo_icd.org::#reg-status][STATUS]]
:MONITOR:  p_tw_busy_follows_start
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: The block shall assert ~busy~ on the clock after ~start~ is
  sampled high and keep it asserted until the clock in which ~done~ pulses.
- Rationale :: Software polls one bit to know whether it may write.

*** REQ-003 Illegal input is ignored
:PROPERTIES:
:CUSTOM_ID: REQ-003
:METHOD:   T
:TEST:     [[file:demo_vplan.org::#TC-10][TC-10]]
:DESIGN:   [[file:demo_hdd.org::#fsm][FSM]]
:ICD:      [[file:demo_icd.org::#illegal-sequences][illegal sequences]]
:MONITOR:  p_tw_no_start_while_busy
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: A ~start~ while ~busy~ is asserted shall have no effect on the
  running operation or on its result.
- Rationale :: A watchdog reboot or a context switch can replay commands.
  The hardware stays correct without the software being correct.

** Reset and start-up

*** REQ-060 Reset state
:PROPERTIES:
:CUSTOM_ID: REQ-060
:METHOD:   T
:TEST:     [[file:demo_vplan.org::#TC-01][TC-01]]
:DESIGN:   [[file:demo_hdd.org::#clocks][REG_RESET]]
:ICD:      [[file:demo_icd.org::#clocks][resets]]
:MONITOR:
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: After ~rst~ the block shall be idle with every register at the
  reset value of the ICD, within 2 clocks of the release of ~rst~.
- Rationale :: Software may touch the block as soon as the CPU runs.

*** REQ-061 Recovery without hardware reset
:PROPERTIES:
:CUSTOM_ID: REQ-061
:METHOD:   T
:TEST:     [[file:demo_vplan.org::#TC-11][TC-11]]
:DESIGN:   [[file:demo_hdd.org::#clocks][SOFT_RST]]
:ICD:      [[file:demo_icd.org::#recovery][recovery]]
:MONITOR:  p_tw_soft_rst_aborts
:RESULT:   PASS
:STATUS:   verified
:END:
- Shall :: Writing ~SOFT_RST~ shall return the block to the reset state
  from any state, including an error, without a ~rst~.
- Rationale :: A CPU-only reboot does not reset the fabric ([[file:demo_icd.org::#recovery][ICD, recovery]]).
